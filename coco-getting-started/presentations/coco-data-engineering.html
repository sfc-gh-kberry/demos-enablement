Three Vendors, Three Formats, One Problem

Each payment processor sends data in a completely different shape

PayRight (Vendor A)

  • Dates: MM/DD/YYYY
  • Amounts: $1,234.56
  • Names: ALL CAPS

SwiftPay (Vendor B)

  • Dates: YYYY-MM-DD
  • Amounts: 1234.56
  • Names: Title Case

QuickSettle (Vendor C)

  • Dates: DD-Mon-YY
  • Amounts: 123456 (cents)
  • Names: lowercase
Goal: Unify into a single FACT_TRANSACTION with consistent schema — using CoCo to write the SQL for us.

Setup (Pre-Lab)

One script creates the database, schemas, and sample data

~30 seconds
-- setup.sql creates the database + 3 raw tables CREATE DATABASE IF NOT EXISTS COCO_DE_LAB; CREATE SCHEMA COCO_DE_LAB.RAW; -- 500 rows per vendor, realistic synthetic data CREATE TABLE RAW.VENDOR_A_TRANSACTIONS (...); CREATE TABLE RAW.VENDOR_B_TRANSACTIONS (...); CREATE TABLE RAW.VENDOR_C_TRANSACTIONS (...);
-- Verify setup SELECT 'VENDOR_A' AS source, COUNT(*) FROM RAW.VENDOR_A_TRANSACTIONS UNION ALL SELECT 'VENDOR_B', COUNT(*) FROM RAW.VENDOR_B_TRANSACTIONS UNION ALL SELECT 'VENDOR_C', COUNT(*) FROM RAW.VENDOR_C_TRANSACTIONS;

Tier 1: Explore & Understand

Snowsight + CoCo Sidebar

Beginner · ~8 min
  1. "What tables are in COCO_DE_LAB.RAW?"
  2. "Profile VENDOR_A_TRANSACTIONS — show me row counts, nulls, and sample values for each column"
  3. "Compare the schemas across all 3 vendor tables. What are the differences?"
  4. "What data quality issues do you see in VENDOR_C_TRANSACTIONS?"
Key Value: Instant data profiling and issue detection without writing SQL

Tier 2: Transform & Standardize

Snowsight + CoCo Sidebar

Intermediate · ~12 min
  1. "Create a staging view that cleans VENDOR_A_TRANSACTIONS: parse dates to DATE type, strip $ and commas from amounts, title-case the merchant names"
  2. "Do the same for VENDOR_B and VENDOR_C, mapping to the same output schema"
  3. "Union all 3 staging views into a single FACT_TRANSACTION dynamic table with a 1-hour target lag"
Key Value: Iterative SQL development — CoCo remembers context and builds on previous work

Tier 3: Build a Reusable Skill

CoCo CLI (Terminal)

Advanced · ~10 min

The Problem

What happens when Vendor D shows up next month? Write it all again from scratch?

The Solution

Create a CoCo skill that encodes the pattern: raw table → dbt staging model + schema.yml + sources.yml

# Invoke the skill in CoCo CLI $dbt-ingest-pipeline # Then provide context: "Here's a new vendor table VENDOR_D_TRANSACTIONS with columns TXN_ID, PROC_DATE, AMT_MINOR_UNITS, MERCHANT, CARD_TOKEN"
The skill generates: staging model SQL, schema.yml with tests, sources.yml with freshness checks
